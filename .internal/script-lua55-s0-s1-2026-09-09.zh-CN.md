## 安全补正与保留语义

`acquireContinuation` 在 Lua 分配前预留唯一槽位并增加实例的未完成执行计数；一次受保护 C callback
完成 `lua_newthread → luaL_ref`，建立 root 后才发布 continuation。callback 仅有平凡局部对象，
回滚票据在 `pcall` 外。LuaJIT 冷期 C closure 创建通过现有 Lua 模块的项目内兼容入口使用 `lua_cpcall`；
标准 Lua 使用零 upvalue C 函数。该兼容头在 `sinclude/`，不安装。

OOM 返回 backend status `-10`，与容量 `-7` 区分。失败不登记等待、不调用 provider；恢复原栈、归还槽位。
分配与参数转换后使用原 invocation 资格重验，保留 standalone/绑定后失效的区别，不跨用户代码缓存 ACTIVE。
原生退休返回 `-1`；现有 `ScriptExecution::invokeStep` 对退休后的返回结果执行丢弃/清理，
因此该情形 runtime failure 日志为空，测试另在真实 backend 返回处捕获拒绝结果。
同步退休后的非零错误记录保持原样，没有修改 Execution 的错误策略。

本补正只覆盖实际 coroutine 创建/登记与其调用资格，不宣称已消除所有冷期 Lua OOM 边界。
没有改变 thread 身份、取消时点、GC 策略、稳定点、预算、frontier 或七组件 owner。

| B0-corrected Lua54 | 5 | 1120 | 82.88 | 86.89 |
| Lua55 | 5 | 1128 | 98.85 | 104.48 |

每组完整运行的 thread create/resume/release 都为 30000000。Lua55 的申请量只比 Lua54 多 8 B/周期，
但这次进程峰值更高；不能用这 8 B 解释全部驻留差异。峰值是独立单次诊断，包含整个进程依赖闭包，
不是稳定的 VM-only 峰值结论。VM tracker 在 state 建立后安装，不覆盖最初 VM bootstrap；
CSV 未导出 allocator failure 总数，不能填写为零。最后一行还未执行 oracle/shutdown/VM 销毁，
`requested-released` 不能在这里当作最终泄漏量，EXE-local allocation accounting 关闭时也不能据零字段声称无 C++ 分配。

**Lua55 软件 VTune。** `profile55-captured` 的目标完整业务、错误与关闭记录均有效；
按 benchmark process 过滤的 module/Hotspots 时间约 56.68 s。采样涵盖冷期、warmup、测量、oracle 和关闭，
不与旧 ROI/phase 百分比直接相减。summary 的进程命令/线程数元数据仍包含捕获 launcher，不能解释成引擎增加了一个执行线程。

| 非重叠 self 样本 | CPU 秒 | 约占目标 CPU |
|---|---:|---:|
| CRT `longjmp` 的内部恢复路径 | 14.901 | 26.3% |
| `malloc_base` | 6.181 | 10.9% |
| `luaD_rawrunprotected` 自身 | 5.496 | 9.7% |
| `free_base` | 2.842 | 5.0% |
| `luaH_Hgetshortstr` | 2.633 | 4.6% |
| `luaV_execute` 自身 | 1.578 | 2.8% |

这里最大的未命名热点不是凭名字猜测：真实 `VCRUNTIME140.dll` 的 `longjmp` 导出 RVA `0x19b50`
在 `0x19b73` 跳到采样热点 `0x1d6d0`；该段恢复通用寄存器、浮点/SIMD 控制与寄存器、rsp 并跳回保存位置。
调用树实际为 `lua_resume → luaD_rawrunprotected → Lua 执行 → lua_yieldk → luaD_throw → longjmp`。
因此它包含正常 yield 的非局部返回，不是脚本错误，也不是新创建保护的全部开销。
另一个实际机器码入口 `luaD_rawrunprotected` 调用 `__intrinsic_setjmp`，两者应分开讨论。
导入/导出、两侧反汇编和 CRT 哈希与采样一并交付；没有把单条 `fnclex`、CET 分支或 cache miss 认定为已测根因。

模块 self 时间约为 Lua VM 34.5%、两个 CRT 模块合计 42.7%、Script 核心 17.7%、Lua backend 4.4%。
这支持“Windows 标准 Lua 的非局部返回、分配与 VM 访问值得后续分别调查”，
不支持删除现有保护，或把所有差距算到 `invokeAccess`/`resumeOne`。
本轮没有因此改异常模型、GC、VM 私有实现或打开 S2/S3 实验。

## 支持范围和保留限制

沿用 [SR-5 支持与构造合同](script-system-sr5-implementation-2026-09-07.zh-CN.md)、
[初始资格补正](script-system-sr5-admission-correction-2026-09-07.zh-CN.md) 与
[SR-6 总结](script-system-sr6-summary-2026-09-07.zh-CN.md)。首批不扩类型、不复制账本。

- Lua55 保持默认 int64/double，但 Lux value codec 仍拒绝 i64/u64 等原来不支持的类型；
  已核对 i32/u32 范围、2^53 附近 f64、NaN/Inf/-0、整数运算与真实生成输入。
- 官方 Lua55 以 C、共享 DLL、/MD、RelWithDebInfo 构建；没有切换 C++ 异常模型、GC 策略、extra space 或语言可见 thread 语义。
  收口时核对[官方缺陷页](https://www.lua.org/bugs.html#5.5.1)，当时 5.5.1 项下没有列出的报告；
  这不等于证明无缺陷。`upstream-review.json` 记录实际读取时间和响应哈希，不倒填为开工时的捕获。
- 引擎各侧统一 RelWithDebInfo；LuaJIT/Lua54 复用既有固定 DLL/头/包身份，没有本轮重建。
  未将无法完整关联到现有 DLL 的历史编译开关伪填为 Lua55 wrapper 的开关；跨 VM 比较包含现有依赖包差异，
  不能把总差值全部归因于版本算法。工作负载 seed 固定；生产仍用各 VM 的 `luaL_newstate` 默认 seed 策略，
  自定义 allocator 测试的 Lua55 seed 才显式设为 1592598566。
- `global` 默认兼容行为保留；Lua55 for 变量只读。文本制品重新 cook，wire/schema 没有变更。
- `lua_dump`、`lua_load`、`lua_pushvfstring`、`lua_resetthread` 没有本仓实际调用，不新增无业务的适配层。
- Windows x64 是本轮实际验证环境。Linux recipe、Android/iOS/console、ASan/UBSan 和 PMU 未获验证；不能从 C 可移植性推导平台资格。
- 原 `update-heavy` 名称对应的是脚本字段递增，并非复杂游戏逻辑；Physics 混合是真实查询与 Event/NextStep 业务，
  checksum 只覆盖 C++，Lua 侧检查返回 bool 和 payload。其原驱动没有完整累计错误/关闭结果导出，这些字段保持未知。
- 既有 churn 驱动在 8 配置时每轮重建 1 个，在 8192 配置时每轮重建 100 个。
  报告按实际重建数归一化，不把它当作单实例规模扫描等价证明。
- 逐 continuation 的 wall-clock 恢复延迟没有独立时间戳，不能用批次 p99 冒充该指标。
  此前性能债务与未解释份额仍保留；本轮没有开启后续架构或 GC/allocator 优化。
- 启动 capture 的 `.strip()` 丢掉 porcelain 第一行前导空格，导致 main 的 `.gitignore` 初始哈希漏记；
  初始 dirty 状态仍有记录，本轮没有编辑该文件。修正工具只影响后续捕获，不回填伪造启动哈希。
