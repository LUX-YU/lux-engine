# Editor 代码质量规范

**适用：P10Q、P11、P12、P13 及后续 Editor 修改。**  
**日期：2026-09-30**  
**地位：与 P10Q 实施文档配套的规范；不是另一套架构，也不是验收通过声明。**

本文件是 QR01–QR22 的唯一现行规范。施工状态只记录于 `.internal/editor-redesign/` 的迁移账本；本文件不宣告任何阶段通过。历史验收材料按固定实现 SHA 保持原样。

## Framework v2 适用范围

新框架以用户确认的 Framework v2 终态规范为准：EditorComposition 只构建声明，完整 Context 的运行目录不再登记或 freeze；项目级唯一服务 owner、
Root 唯一拥有顶层 Pane，Object parent 仅维护结构，不继承旧五层、全局命令目录或服务 Scope。
QR02 的描述式依赖/Scope 要求仅作为 legacy 历史规范保留；活动路径使用 EditorComposition 声明与
EditorServices 惰性唯一 owner，不另建 scope、依赖图或通用容器。工厂创建后保存准确依赖，
运行目录不成为热路径服务定位器。其余代码风格、错误、寿命与完成交付原则继续适用。
历史验收和延期判定不因本次框架替换而改变。

## 1. 优先级与总原则

需求和真实业务语义优先于模式名称、历史类型草图、文件数和测试数量。原阶段中“不得改目录”“暂保某接口”等范围限制，不是永久设计正确性的证明；P10Q 明确调整的路径以新决定为准。未被 P10Q 改动的行为、数据格式、已验证身份与寿命契约继续有效。

**一句话：一份事实、一份 owner、一套实际算法；提供者和消费者共享准确契约，而不是长期靠同义转换互相补偿。**

## 2. 必须遵守的规则

### QR01 — 先写责任，再决定类型

每个新生产类型必须能回答：它拥有哪份事实或资源；谁构造和销毁它；是否跨回调或线程；为何不能直接用现有类型或自由函数。仅有 `static start()` 的无状态类不叫 Operation。真正拥有任务、内容版本、取消或结果责任的操作对象不能简化成丢失这些责任的 TaskId。

不要求每个类都有接口。继承只用于真实替代关系、对象协议或已经存在的 polymorphic 边界；依赖和资源 owner 默认组合。纯值不因“统一对象体系”而继承 LuxObject。

LuxObject 父链不拥有孩子。Root 通过唯一 SparseSet 拥有窗口；内容由成员或智能指针拥有。
结构登记不改变 C++ owner。Runtime 负责身份和安全回收，不成为第二个对象 owner。

### QR02 — 声明式依赖与受约束创建环境

允许服务/UI 工厂在创建边界从已注册描述进行类型化解析，如 `get<T>(scope, key)`。
工厂须声明依赖、实例范围与配置合同；缺失、歧义、循环、代次或配置失配准确失败。
创建后对象保存自己的准确依赖，不在热路径反复解析；首次启动新用例也属于创建边界。

禁止全局可变 service locator、`map<string,any>`、不断增长的具体 getter、把全部 Application
字段搬进 Context、业务强持无限可变环境，以及注册时构造全部服务。UI 工厂可使用 workbench
共同 EditorContext；无 UI 服务只能使用无 UI resolver 和明确依赖。引擎基础借用不得伪装成共享拥有。

### QR03 — 事实通知复用 LuxObject

控件事件与提交后的变化通知使用现有 TSignal/Connection。需要接收端生存期管理时使用正式接收者连接；lambda 捕获不自动延长所捕获对象寿命。

发送时点必须写清：准备未成功不得发“完成”；信号部分广播成功不能整批重发。FULL/CLOSED 的处置与 revision/resync 明确，不自建另一份订阅表或通知线程。

### QR04 — 查询和准入不是广播

有返回值的同步查询、校验和准入使用具体方法或必要的 typed role，返回准确 Result。不要把信号的 delivery 成功当业务接纳，也不使用通用 action 编号加巨大错误 variant 掩盖不同语义。

编译、发布、保存基线采用、打开内容和显示视图分别报告自己的事实。命令 UI 可以汇总状态，但不能改写这些事实。

### QR05 — 有限异步工作只走原 Process

复用 ExecutionRuntime、Task/TaskScope、已有 CPU/blocking scheduler、TaskReporter 和完成分发。不新增私有 thread pool、`std::async` 旁路、永久轮询线程或第二任务状态库。

计时、进度和取消继续使用既有设施。线程 ID 的使用或 test-only 线程不等于违规；禁止规则不能机械匹配 `<thread>`。

### QR06 — 已接纳工作的完成必须可靠结清

新业务可以因 BUSY/容量被拒绝；已接纳工作的唯一完成不得因此被丢掉。完成吸收可作为不执行任意业务回调的窄步骤，实际业务采用另在安全点进行。

内层完成或清理不得解除外层 dispatch。取消意图、任务完成、业务采用、文件发布和 GPU 退休不能互相替代。UI 销毁不取消其未拥有的业务记录。

### QR07 — 代码生存期覆盖对象和错误值的最后使用

动态对象、memento、encoder、错误 payload、闭包及 deleter 必须在代码释放前完成最后析构。除了普通析构，还检查移动赋值、替换、早返回、拒绝准入和回调中的清理。

`shared_ptr` 的数量不是控制责任协议。外部 code owner 放在正确的拥有单元，不能只将 lease 放进插件对象自身后就宣称虚析构尾部安全。

每个对象只有一个实际删除责任。动态 deleter、析构返回及控制块清理使用下层代码保活合同；
最后共享引用在 worker 释放时，实际 affinity 析构回到原对象 owner 的安全点。成员不得独立请求 delete。

### QR08 — 草稿必须携带真实来源

显示缓存、可提交草稿、排队意图与作者 current 是不同事实。草稿值和 `based_on` 同次捕获；一般刷新不重写草稿来源，BUSY 重试不补 latest。

STALE 明确拒绝，允许显式 Revert/重新选择；不能自动覆盖新内容，也不能让终结失败永久堵塞队首。GraphCanvas 保持领域无关，由具体工具附加来源。

### QR09 — 对外边界验证，受控内部复用结论

工厂建立必需依赖和不可变配置的不变量；对外入口完成身份、类型、线程和长度验证。无回调、无挂起、无失效操作的内部连续段复用引用，避免重复 lookup/describe。

跨 callback、任务等待、下一帧、容器回收、History/绑定变化、文件 IO 的结论必须重新证明。不能把“检查过一次”写成永久正确的凭据。

### QR10 — 删除判断必须有有效期证明

每处检查合并或删除记录：首次证明点、使用点、之间的失效可能、是否为公开 SDK 入口、替代类型/断言、回归用例。

不得为了少 if 删除真实文件发布前版本复核、Store 代际检查、预算溢出检查或回调防删除。内部断言可以表达不变量，但 release 构建不能依靠 assert 拒绝外部非法输入。

### QR11 — 不存在、暂时不可访问、真正失败分开

BUSY/权限/IO 不是 STALE_SESSION、空目录或文件不存在。保留原值不等于报告成功。关闭准备区分可重试、已结束与永久拒绝；不得把所有领域错误转换成 BUSY。

诊断保存到异步或结果记录中时必须拥有文本或稳定来源，不能引用临时字符串。

### QR12 — C++20 是真实构建约束

第一方目标和安装公共头在声明的 C++20 模式下编译，关闭非必要语言扩展。继续使用 `lux::cxx::expected`；不无条件引入 C++23 的 `std::expected`、`std::scope_exit`、`std::move_only_function` 等。

Rule of Zero 优先；自定义析构和资源替换须检查特殊成员。固定地址 owner 明确禁止复制/按值移动，拥有单元可按实际语义 move-only。不追求 concepts/ranges 使用数量。

### QR13 — 借用与拥有回调必须区分

立即调用可用模板或实际版本的 `lux::cxx::function_ref`，不保存后者；当前对象绑定为 lvalue，不能假设临时 lambda 或 noexcept signature 均受支持。

延迟唯一闭包用实际 `move_only_function` 或现有 owning callable；确需复制才保留 std::function。Delegate 是非拥有类型化调用，不具备 Connection 的自动断连能力。没有真实调用需求就不将普通方法改造成 callback。

### QR14 — lux-cxx 复用以资格和测量为依据

记录真实安装依赖的提交/头/库，而不只看 README。使用 StableSlotMap、SmallVector、SparseSet、SharedBytes 等前，明确 key 范围、地址稳定、构造失败、代际、预算和清理规则。

StableSlotMap 不保护 erase 中的回调；SparseSet 不适合任意 UUID/大 hash；自动复用 key 不能替代作者身份高水位；SmallVector 不保证所有捕获/列表都无分配。局部 PMR 计数不得写成整个进程峰值。

### QR15 — 索引是派生数据，不是第二个 owner

允许唯一对象表派生 by-id 索引、父索引和查询缓存，以减少重复扫描。完整构建后发布，失败不能留下半份索引。缓存键包括其实际来源域和版本。

小容量线性扫描可以有理由地保留。不得一律换散列，也不为每个 getter 加一份缓存。能用一次遍历解决的全图验证，不应逐点重扫完整祖先链。

### QR16 — 性能证据必须可比较

对改动路径记录算法计数、规模、构建模式、预热、样本和分配/复制的覆盖范围；延迟至少区分中心与尾部。保留无收益与回退结果。

禁止把进程启动总耗时作为热路径，把 debug/sanitizer 与优化构建混比，或用“容器更先进”代替实测。大规模优化不自动成为所有后续阶段的额外范围；先改真实缺陷和已确认成本。

### QR17 — 目录按功能主题组织

不新建 adapters、ports、managers、common2 这类模式目录来安置职责不清的代码。真正文件后端、执行接线、共享视口分别回到正式功能主题。

允许同主题多 target；允许不同层共用准确类型。文件短不必合，文件多不等于解耦。无状态壳、纯别名头和无独立责任的微型转发应收敛；独立 RAII、平台源、公共不变量和测试不按行数自动删除。

### QR18 — 公开依赖应能独立使用

PImpl 私有依赖留 CPP；引用/指针在合适处前置声明；基类、值和 variant 的完整定义不能省。头文件 self-contained，不靠包含顺序。

不通过 sibling 的私有 include 目录取得实现。Material 需要通用视口不能链接完整 Scene Inspector/创建/codegen 包。不得用巨型 editor_common 或重新开放 Context 解决依赖循环。

### QR19 — 构建模块不等于动态装载单元

内部 Editor 实现默认 STATIC；纯契约用确实合适的 INTERFACE。插件和跨 DSO 共享唯一状态的边界按实际消费者决定，不一刀切。

审核 File API、实际链接/装载、PIC、visibility、CRT、allocator 和本地静态身份。不能从 exe 导出全部内部符号，也不能通过关闭插件功能“减少 DLL”。P11 对外插件验证与 P13 完整安装资格仍需执行。

### QR20 — 平台能力与测试分组必须真实

CPU native 不强制要求 GPU 或 Windows linker。跨平台生产代码编译与平台专用运行测试分开；开启一组测试不能偷偷禁用整个功能模块。

平台调用在原平台实现或 test-only 源；路径大小写、Unicode、空格、固定宽度和对象格式正确。`lld-link` 不能直接改名为 `ld.lld`。缺环境明确 PARTIAL/NOT_RUN，不算通过；既有历史失败和首次冷构建事实保留。

### QR21 — 不保留永久源码兼容层

本阶段替换的公开 C++ 接口同步更新真实消费者、CMake、生成器、SDK 和活动测试，删除旧 alias/forwarding header。不能用接口名字清零代替删除真实旧责任。

尚有实际消费者的其他历史桥只按原 P12 期限暂留；不得新增 New/Legacy2 回落体系。旧资产/布局的只读兼容与失败夹具继续保留，它们不是应删垃圾代码。

### QR22 — 证据、阶段与权限不混淆

P10Q 成为显式阶段，并由 P11–P13 继承质量规则。当前测试允许按新 API 映射保留等价/更强行为；历史收据按各自固定提交验证，不改写。

代码审核、脚本自检、编译负例、真实 SDK、GPU、IME 和跨平台构建分别报告。实现与证据分别提交；保存用户修改，不擅自改 main、合并、删分支或发布产品。

## 3. 后续阶段的具体继承

| 阶段 | 必须继承 | 仍属于该阶段本身的成果 |
|---|---|---|
| P11 | typed provider；原 LuxObject/Process；准确 owning callback；固定注册快照；不过度 Port/Adapter 化；运行 SDK 不耦合 Editor-only 变更 | 命令 query/execute、不可变扩展发布、worker decode/owner 构造、外部安装扩展、C03 责任 |
| P12 | P10Q 的目录/接口/库选择；草稿来源；真实发布结果；准确生命周期；同一写协调器 | 完整 Open/Reload/Close/SaveAll/Layout/Restore/Exit；唯一产品入口；所有到期旧 owner/桥删除 |
| P13 | 干净安装/平台/性能证据口径；受控容器资格；后续新增代码也服从上述规则 | 最终 Windows/Linux、完整 GPU/IME 适用矩阵、长期容量和延迟；所有剩余工程资格 |

P12 不得重新创建已删除的 ProjectCatalogAdapter、TaskQueryPort、静态 Operation class 或 adapters 分类。P13 若发现 P12 到期旧 owner，须明确回报 P12 未完成，不将其再列为下一版的可选整理。

## 4. 每次实现提交的最小审查问题

代码审查至少回答下列问题，答案落在对应代码/测试/清单，而不是只写“符合规范”：

| 方面 | 审查问题 |
|---|---|
| 责任 | 是否新增第二份事实、owner、任务目录或手工寿命协议？ |
| 组合 | 提供者和消费者是否使用同一准确类型？有无只为转发而新增类型？ |
| 时序 | 借用、来源和检查的有效期是否跨回调/异步？完成是否可能丢失？ |
| 结构 | 修改一个简单行为是否需要同步很多同义壳？是否无故增加新 target/DLL？ |
| 性能 | 热路径有无新增全量复制、嵌套扫描、永久增长或分配？测到了什么？ |
| 平台 | 新调用、生成器和测试条件在声明支持的平台是否实际可构建？ |
| 验收 | 原语义有无被删；未测内容是否准确；用户文件和历史证据是否受保护？ |

这些审查问题不意味着每次 PR 都重跑所有长期基准。CI 按受影响模块运行精确单测/负例/边界；需要真实设备的测试使用已声明环境；阶段封存时执行完整适用矩阵。任何依赖门禁都不能独自证明接口优雅或生命周期正确。
