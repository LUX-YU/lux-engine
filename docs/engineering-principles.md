# 通用软件设计与 C++ 工程规范

软件应让读者沿着类型、数据流和调用顺序理解其行为：谁负责决策，谁持有数据，谁执行动作，何时发布
结果，何时可以释放资源。正确性主要来自明确的结构与合同，而不是不断追加包装、共享保活和重复检查。

本文适用于本工程的基础库、业务模块、工具和应用，不要求使用某个后端、固定线程数、特定执行框架
或统一的库拆分方式。它总结可迁移的设计原则，并结合 [AGENTS.md](../AGENTS.md) 和
[.clang-format](../.clang-format) 给出本工程的 C++ 与 CMake 约定。具体模块的协议、生命周期和
性能目标由该模块另行定义，不应冒充全工程通用规则。

## 1 设计决策的优先顺序

1. 保证可观察行为、数据完整性、身份、线程与资源寿命正确。
2. 明确职责和事实来源，降低理解与维护成本。
3. 选择符合访问模式的数据结构和算法。
4. 根据真实工作量优化时间、空间、同步和调用成本。
5. 用清晰的类型、命名、文件和格式表达上述设计。

源码行数、类型数量和局部微基准用于辅助判断，不能单独决定设计优劣。一个清楚的算法函数可以比
数个相互转发的小类更容易维护；删除必要的状态和错误处理，也不会因为代码变短而成为改进。

已有代码不是必须保留的架构前提。允许调整类、函数和目录，但必须迁完真实消费者。提交过、测试
通过过，都不能证明当前职责划分合理。

复用成熟实现时，应理解并保留其数据结构、不变量、复杂度和失败处理。可以迁移算法而重新安排模块
边界；不要只借用成熟实现的名字，却重新写出一套更复杂或更低效的机制。

## 2 职责应由实际行为决定

### 2.1 动作归执行者

方法属于实际执行动作、维护相关不变量的对象。参数和记录描述工作，不应因为保存了一个控制器指针
就反向调度整个系统。

```cpp
queue.consume(message);
allocator.release(range);
writer.write(document);
```

上述关系分别表示队列消费消息、分配器归还范围、写入器写文档。不要为了调用外观一致，把它们改成
消息自行控制队列、范围自行安排分配流程、文档自行寻找写入器。

数据类型仍可以有维护自身值语义的方法，例如比较、计算长度或规范化内容。操作对象、迭代器、订阅
连接也可以持有必要的上下文借用。判据是方法是否符合该类型的真实含义，而不是所有 struct 都必须
没有方法、所有指针都必须消失。

### 2.2 拥有组件不等于实现组件的全部行为

一个对象可以负责若干组件的装配和销毁，但组件的内部初始化、算法和状态转换仍应归组件自身。
装配入口不应直接填写另一个对象的大量私有字段，再通过 friend 绕过它的职责边界。

上下文应提供明确的一组依赖，不能成为任意代码随时查询全部系统状态的服务容器。一个函数只需要
文件访问能力，就不应借用整个应用对象来间接取得它。

### 2.3 抽象必须消除重复或表达真实差异

引入长期类型前，应说明它的独立职责、实际数据、消费者、结束条件，以及现有对象为什么不能承担。
只有算法而没有独立状态时，优先使用普通函数；只有短期数据时，优先使用局部值。

不因为可能存在未来后端，就提前增加接口层、工厂层、注册层和转发层。出现真实的不同消费者或实现
之后，再抽取稳定的共同合同。抽象的收益是减少需要维护的机制，而不是使类型图看起来更完整。

Manager、Host、Owner、Context、Provider、Adapter 等词不能替代职责说明。名称不清时，先检查是否
尚未决定它到底负责什么，而不是换一个同样宽泛的词。

## 3 数据与事实来源

### 3.1 同一事实只由一处决定

身份、成员关系、业务状态、执行进度和结果交付是不同事实，应分别找到真实责任主体。不要让多个
布尔量、引用计数、目录和容器成员关系重复决定同一个对象是否有效。

冗余缓存必须说明它从哪份数据派生、何时失效、由谁更新。无法说明这些条件的缓存通常会成为第二份
权威数据。必要的计数并非都应删除：容量、在途操作数和外部回调数可能表达不同的约束。

### 3.2 业务意图与内部实现状态分开

调用方决定自己业务中的关系和操作顺序；库完成声明过的工作，不擅自推断意图或自动修补调用顺序。
如果库需要维护依赖关系，这必须是其明确职责，而不是为了容忍错误使用临时增加的机制。

库仍负责自己的内部状态。不能把内部地址变化、分配器扩容、线程同步或外部操作完成条件推给调用方，
也不能以“调用方知道业务变化”为由省略库自身的资源安全。

### 3.3 身份不等于地址 名称或 Hash

当对象可以销毁、复用或跨边界引用时，使用能表达真实身份的句柄。需要 generation 的地方不能只靠
裸地址或可复用下标辨认旧对象。

名称用于发现，已解析的身份用于执行。拿到可靠 ID 后直接定位，不在下游重复字符串查找。Hash 可以
加速比较，但不能单独证明完整名称、类型或布局相同。

类型身份、实例选择键和用途说明应分别定义。换一个实例键不会改变所属类型的数据合同；仅用于
阅读和展示的说明文字，也不应参与类型相等或 ABI 判断。

## 4 所有权 借用与资源释放

### 4.1 在真实拥有者上表达 RAII

RAII 的目的，是让拥有者在所有结束路径上完成正确释放。它不要求每个叶子记录都有析构器，也不要求
为固定成员再增加一个动态删除器。

对大量资源，允许用轻量句柄和实际集合统一管理；对独立资源，允许由独占对象管理。每个记录只携带
释放或使用它真正需要的信息，不重复保存可以从明确上下文取得的整套环境。

采用裸句柄时，必须明确谁释放、何时转移，以及创建失败怎样回滚。不能把“所有权清楚”简化成依赖
所有调用者永远记得手动释放。

### 4.2 指针形式按需求选择

| 需求 | 常见表达 |
|---|---|
| 固定存在 与包含对象同寿命 | 值式成员 |
| 只在一次调用期间访问已有数据 | 引用或 `span` |
| 可选借用 | 明确可空的指针 |
| 独立对象或异构实现的独占拥有 | `unique_ptr` 或已有独占容器 |
| 地址必须稳定 | 稳定地址容器或有依据的独立分配 |
| 多个独立消费者确实共同决定寿命 | 经证明的共享所有权 |

`unique_ptr` 没有引用计数，也不自行创建所指对象的分配。需要审查的是不必要的独立 `new`、两层
对象和动态删除器，不能把去掉智能指针本身当作性能结论。

默认优先独占与受控借用。使用 `shared_ptr` 前，必须说清楚有哪些独立消费者、为什么不能通过已有
拥有者保证寿命，以及最后释放发生在哪里。不得用共享保活掩盖错误的析构顺序或悬空借用；也不应把
某个模块禁止共享所有权的局部裁决扩大成所有软件的禁令。

### 4.3 移动必须体现实际转移

对只含指针或整数句柄的聚合调用 `std::move`，并不保证移出对象为空。转移拥有权时，应按实际类型
显式清空源，且不能覆盖仍然有效的目标资源。

```cpp
destination = std::exchange(candidate, {});
```

这要求目标已经为空或原内容已正确处理。资源“从目录移除”“操作已返回”“底层使用已结束”也不是
同一件事，释放条件不能从其中任意一个事实猜测出来。

### 4.4 借用必须写明结束条件

借用合同至少说明：谁提供数据、允许谁读写、有效范围、何时结束，以及失败、取消和断连后的处理。
异步借用不能仅写“调用期间有效”，因为函数返回可能早于实际读取结束。

回调可能来自动态库时，提供函数、类型操作和删除器的代码必须覆盖最后一次调用及退栈。对象销毁
完成不自动证明外部调用栈已经返回。

析构顺序必须可读。C++ 成员析构发生在析构函数体之后；在函数体中提前销毁共享设施，可能使随后
析构的成员失去依赖。局部构造回滚与最终关闭应采用一致的资源释放规则。

## 5 异步 并发与生命周期

### 5.1 复用已有执行机制

通用调度、操作状态和停止机制优先使用已有执行设施或标准化协议。已经采用 Sender/Receiver、
Scope 等机制时，不再旁置一套承担同一职责的任务拥有表。

同步操作保持同步，不为了统一接口而强制创建 Future、Sender、线程或堆状态。真正的外部异步源
可以需要专用适配，但适配只表达该源缺少的接缝，不扩展成新的通用框架。

### 5.2 生命周期域按责任划分

操作状态、已完成结果、外部系统仍在使用的资源、生产者回调栈可能分别结束。不能把它们都压成一个
完成标志，也不能在每个嵌套对象上重复增加 Scope、引用计数或 Pending 表。

是否需要独立生命周期域，应由准入、取消和结束责任决定。既不能每层一套，也不能不分语义强行只留
全系统唯一的一套。所选执行设施能保证什么、不能保证什么，必须在边界说明。

### 5.3 取消 失败与已发生的副作用分开

请求取消不等于外部操作已撤销，连接关闭不等于后台读取已经结束，提交接纳不等于持久化或设备执行
已经完成。接口应明确其成功终态代表哪个事实。

不可回滚副作用发生前，先准备必须的容量、结果落点和保活条件。失败时保持旧状态或准确报告实际
影响；不能在副作用已经发生后才发现无法保存结果，再把它描述成确定取消。

### 5.4 交接和重入有固定边界

线程安全首先来自明确的线程归属、不可变输入、消息交接和发布点，不以全局锁包裹所有行为。
回调允许同步完成时，必须考虑 `start()` 内就结束、Receiver 调用中销毁状态及回调尾栈仍在访问数据。

从就绪集合取出节点后再调用用户代码；调用后不访问可能已被销毁的节点。批量派发有明确边界，派发
期间产生的新工作不能无意形成无限自喂循环。等待前后的就绪检查与通知协议必须避免丢唤醒。

停止流程应按真实依赖顺序推进：关闭准入、停止生产、处理已接纳工作、完成必要交付、结束回调、释放
被借用设施。不能在需要当前线程继续推进的工作上阻塞等待，也不能通过反复全局等待补偿顺序不清。

## 6 阶段 事务与增量处理

把流程划分为输入验证、准备候选、提交、发布和回收等实际阶段。每个阶段的前置条件、允许副作用和
输出应明确；已证明的条件由后续代码使用，而不是每层重新推测。

查询不应暗中触发昂贵初始化，事件派发不应隐藏新的事务提交。确需组合这些行为时，在负责流程的
调用点明确写出顺序。

需要一致采用的一批变更先整体验证，再修改权威状态。暂存数据按变化量增长，不为了回滚复制整个
大集合。发布前失败保留原状态；发布后的错误按实际副作用处理。

多个操作并行使用同一数据时，必须有独立可变存储或可靠顺序。轮转了几个索引，不代表对应资源就能
安全复用；复用必须依据实际使用结束条件。

更新应处理真实变化的 K 项及其受影响消费者。零变化的更新收集不应遍历全部 live 数据；连续工作
应在保留依赖和错误边界的前提下批处理。不能只减少外层调用，却在内部继续逐元素分配、提交或同步。

## 7 事件与观察机制

观察事件不等于可以立即修改被观察系统。若通知发生在容器或对象修改过程中，后续结构修改应转交到
已经定义的安全点；不要依赖某个容器当前恰好容忍重入。

订阅建立前已有的数据也需要处理。设计应明确如何协调存量快照与增量事件，避免漏掉先存在的对象；
并发场景还需处理快照与订阅之间的竞争，不能机械套用固定调用顺序。

只有通过会发布事件的写入入口，观察机制才有完整语义。直接修改字段绕过通知时，不能期待订阅者
自动得知变化。销毁通知中仍然有效的数据应及时提取，不能假设对象销毁后字段仍可访问。

结构性变化适合由明确事件驱动；异步结果到达可能需要完成队列或适当轮询。选择依据是生产者的真实
完成协议，而不是强行把所有流程改成观察者。

## 8 接口 结果与错误

### 8.1 返回值表达调用者实际需要的区别

| 语义 | 推荐表达 |
|---|---|
| 纯真假判断 | `bool` |
| 没有失败生产者 | `void` 或自然值 |
| 一个结果和有意义的失败原因 | `expected<T, Error>` |
| 底层状态已完整表达结果 | 在相应边界保留或转换一次 |
| 查询已有稳定数据 | `const T&`、`span` 或有明确缺失含义的借用 |
| 大结果且无法确认廉价移动或消除复制 | 输出引用加必要的状态返回 |

自然语言中的“成功/失败”不代表所有错误都能压成 bool。超时、容量不足和输入不支持若需要不同处理，
就必须保留区别。没有失败来源的内部设置也不应产生层层 expected。

类型大小不等于返回成本。保证的复制消除、非保证的 NRVO、廉价移动和深复制应分开判断。输出引用
必须规定失败后的状态，不能留下半构造资源或悬空引用。

消息结果可以采用显式错误字段与业务数据，内部函数也可以使用 expected，两者按各自边界设计。
不能把一种模块的消息形状强加给全部 API。含有 vector 或字符串的结果不是平凡字节块，不能直接
按裸内存布局跨不相容边界传输。

### 8.2 校验集中在真实边界

外部输入、身份、类型、范围、准入和外部状态变化必须检查。已经由所有权、类型和前序验证保证的
事实，不在后续每层重复检查。异步期间条件确实可能失效时，采用结果的边界仍需重新确认。

不要将“信任调用方”解释为接受越界访问，也不要将“防御式编程”解释为对每个内部不变量重复加分支。
检查的位置应由不变量在哪里建立、在哪里可能被打破决定。

### 8.3 错误与诊断不成为第二套控制流程

本工程的语义错误不使用 C++ exception，默认采用 `noexcept` 与明确错误值。普通 new/STL OOM 为
fatal，不虚构可恢复的分配失败；设备、显式容量和外部服务失败按真实语义报告。

生产代码不主动 throw，执行热路径不增加 try/catch。第三方或插件边界的异常隔离遵守 AGENTS.md，
立即转换为工程错误，不让异常穿过不允许的 ABI；不得因此全仓启用禁异常编译开关。

本工程生产接口不依赖 RTTI，不用 `dynamic_cast` 或 `typeid` 弥补不明确的类型合同。需要跨边界
识别类型时，使用已有的显式类型资格机制，不再创建第二套类型目录。

库提供结构化诊断，应用配置输出位置。失败路径不临时注册错误字符串或决定终端落点。实机必须成立
的错误处理不能只依靠会被 NDEBUG 删除的 assert，也不能捕获错误后静默继续。

## 9 模块 头文件与依赖

模块边界由职责、消费者和依赖方向决定。没有独立消费者的概念目录不必单独成为库；真实独立复用的
能力也不应为目录整齐而强行合并。库数量不是设计目标。

底层不反向依赖高层产品，数据声明不依赖使用它的行为实现。共享编码和类型约定放到双方都能依赖的
下游位置，不通过拉入一个完整系统头取得常量。

本工程使用以下可见性：

| 目录 | 用途 |
|---|---|
| `include/` | 安装的公共合同 |
| `sinclude/` | 项目级可见 不安装 |
| `pinclude/` | 仅模块内部可见 不安装 |
| `src/` | 按实际职责组织的实现 |

公共头只 include 声明和字段需要的依赖。实现用的编译器、解析器或平台库留在源文件和私有头中；
能用前置声明就不通过兼容别名迫使消费者包含完整实现。

可选宏不得使不同翻译单元中的同名类型具有不同 ABI。平台专属操作可以保留在选定实现中，不为消除
少量原生调用再包装整个后端；公开层也不能提供无限制的逃逸入口，让专属依赖重新扩散。

迁移类、命名空间、目录和 target 时同步迁完消费者、安装头和导出，不留下长期转发头、空 target
和旧 SDK 补洞。必要过渡按明确范围使用弃用机制，不把临时兼容承诺变成永久设计。

## 10 命名规则

### 10.1 先表达意义 再统一拼写

类型名说明它是描述、实例、记录、操作还是连接；函数名说明真实动作；字段名说明它保存什么。
`api_`、`state_`、`data_` 等词单独出现时通常不足以解释语义，应加入真实对象或能力的限定。

使用 `Manager`、`Host`、`Owner`、`Provider` 等名称不能免除职责设计。第三方规定的名称与标准术语
保持原样，不靠全仓禁词搜索证明架构正确。

名称中的身份、位置、配置和实现要区分。例如位置选择值没有所有权，类型描述不是实例，记录消息
参数的结构也不是执行器。注释应解释必要的约束，不能长期替错误命名辩护。

### 10.2 本工程拼写约定

| 项目 | 约定 | 示例 |
|---|---|---|
| class 与 struct | 首字母大写驼峰 | `FileReader`、`ReadRange` |
| 成员函数 | 小写驼峰 | `readNext()` |
| 成员变量 | 小写下划线 | `byte_count` |
| private 成员 | 小写下划线加末尾下划线 | `byte_count_` |
| 枚举类型 | `enum class` 与 E 前缀 | `EReadStatus` |
| 枚举项 | 全大写下划线 | `END_OF_FILE` |
| variant 类型别名 | V 前缀 | `VInputSource` |

过长类型可起具有语义的别名。正当的类型命名别名应保留；using 声明不要把当前命名空间内的名字
再次引入自身，这种 no-op 既不提供声明，也不能成为保留 include 的理由。

## 11 C++ 排版与可读性

语言遵守工程的 C++20 基线，排版遵守 `.clang-format` 和 AGENTS.md。格式服务于层次和语义，
不通过机械拆行掩盖过长签名、过深调用或混合职责。

### 11.1 缩进 花括号和空行

使用四空格缩进、Allman 花括号风格，控制流保留 braces。`public/protected/private` 与类花括号
同级。相邻函数定义之间留一个空行，相关语句按语义段落分组。

```cpp
class FileReader final
{
public:
    [[nodiscard]] bool isOpen() const noexcept
    {
        return handle_ != kInvalidFileHandle;
    }

    void close() noexcept;

private:
    FileHandle handle_ = kInvalidFileHandle;
};
```

成员声明在不制造大量空白的前提下按字段对齐。指针和引用符号靠类型一侧，例如 `Record* record`、
`const Record& record`。不把一个函数的结束括号与下一函数定义挤在一起。

### 11.2 120 列与语义换行

单条语句不超过 120 列且层次清楚时保持一行。调用过长时按参数和嵌套层级换行；多行调用、
声明和初始化的结束括号独占下一行，与开始层级对齐。不要把一个完整短表达式切成许多碎片。

长声明优先分离限定符及返回类型与函数名；长返回类型先起有意义的别名：

```cpp
using FileOpenResult = lux::cxx::expected<FileReader, EFileError>;

[[nodiscard]] static FileOpenResult
open(std::string_view path, const FileOpenOptions& options) noexcept;
```

参数较多且声明超过列宽时，继续按参数展开：

```cpp
[[nodiscard]] static FileOpenResult
open(
    std::string_view path,
    const FileOpenOptions& options,
    std::span<const SearchDirectory> search_directories
) noexcept;
```

多行聚合初始化保留最后一个元素与结束花括号之间的换行：

```cpp
const ReadRange range{
    offset,
    byte_count,
    destination
};
```

函数签名需要不断换行时，也应检查是否传入了多组无关参数、互斥状态或整个系统上下文。

### 11.3 复杂判断保持短路安全

多个独立校验使用具名 `const bool` 表达语义，再组合判断。名称说明 `has_*`、
`is_invalid_*` 或 `is_*_mismatch`，不把所有条件挤成一条难以审查的表达式。

```cpp
const bool has_record = record != nullptr;
if (!has_record)
{
    return lux::cxx::unexpected(EReadError::INVALID_RECORD);
}

const bool is_type_mismatch = record->type != required_type;
const bool is_invalid_offset = offset > bytes.size();
const bool is_invalid_range = is_invalid_offset || length > bytes.size() - offset;
const bool is_invalid_request = is_type_mismatch || is_invalid_range;

if (is_invalid_request)
{
    return lux::cxx::unexpected(EReadError::INVALID_REQUEST);
}
```

这里先确认 record 存在，再读取字段；通过 `||` 短路避免无符号减法下溢。提取布尔量不能把原来
受短路保护的指针访问、迭代器解引用或算术提前执行。

### 11.4 注释 lambda 与局部抽取

注释说明不变量、借用范围、提交点、线程归属和非常规算法原因，不复述明显代码。局部函数和 lambda
应有可读的责任范围，不用大量捕获藏入新的长期状态，也不为每层转发再建立一个结果包装。

为了缩短某个函数而抽取的辅助函数，必须仍有清楚输入输出。不能把它依赖的整个可变对象搬进一个
“上下文”，使函数表面变短而实际依赖更宽。

## 12 CMake 与构建接口

多行 CMake 调用按参数语义分组，结束 `)` 独占一行，相邻调用之间留空行。文件按所属 target 编译，
不让多个消费者通过重新编译同一生产源来取得内部能力。

```cmake
add_library(document_codec STATIC
    src/Decoder.cpp
    src/Encoder.cpp
)

target_include_directories(document_codec
    PUBLIC
        "$<BUILD_INTERFACE:${CMAKE_CURRENT_SOURCE_DIR}/include>"
        "$<INSTALL_INTERFACE:include>"
    PRIVATE
        "${CMAKE_CURRENT_SOURCE_DIR}/pinclude"
)

target_compile_features(document_codec
    PUBLIC
        cxx_std_20
)
```

真实依赖分别声明 PUBLIC、PRIVATE 或 INTERFACE，不通过多余传递依赖让消费端偶然编译通过。
安装后的头、目标和依赖应构成真实闭包；生成器使用的头版本也必须与当前合同一致。

构建、安装、代码生成和测试输入应能从跟踪源码与已声明依赖重建。不能依靠被忽略的本地源文件、
过时 SDK 或占位 target 补齐配置。

## 13 性能与复杂度

先看算法和数据访问，再看局部指令。针对实际工作量记录访问元素数、复制字节、分配次数、调用次数、
同步次数和峰值内存，不能只看函数是否短、是否用了模板或智能指针。

已知身份适合直接索引；冷态名称查找、排序和图算法有各自成本。处理 K 个变更应尽量与 K 及实际
输出相关，不重复扫描所有对象。对很小的固定集合，线性扫描可能比额外索引更简单、更便宜。

热路径避免重复配置解析、名称发现、编译和无依据分配；异步任务可以有合理的操作状态成本。预分配
需要同时考虑长期保留内存，不能用无限增长缓存制造“零分配”指标。

每次复制都应能说明来源、目的、有效期和必要性。删掉复制不能以延长不可控借用、丢失恢复能力或
破坏并行使用为代价。

性能实验固定输入、工作量、配置和测量边界，采用重复、交替运行并保留异常样本。耗时、等待、启动、
输入准备和外部设备执行分别统计；分析工具的采样和包装计数不能混入正式时延成绩。

热点说明时间花在哪里，不自动证明因果。只有通过受控变化和同工作量比较后，才据此采用最小修正。
未知符号、未测缓存行为和未归因退化如实保留，不能凭推测增加缓存、线程池或新的异步层。

## 14 验证与实施节奏

测试按真实风险和职责闭环组织。日常允许必要的编译诊断、静态审查和针对性复现；完成一个大模块的
接口、实现、消费者和失败路径迁移后集中验证，不每修改一个函数就重跑全部矩阵。

回归要验证外部事实和关键不变量，避免只镜像实现。不能删除失败测试、削弱断言、增加兼容层或以
某个局部目标通过代替完整依赖闭包。正确性失败先处理，不推进依赖该条件的后续工作。

本工程正式构建按 AGENTS.md 执行完整 `all -j 4 -- -k 0`；配置变化后第二轮应无工作。构建与运行
验证串行。文档或低风险可逆修改只执行与变更相称的检查，不为形式增加没有信息增益的测试。

独立验收绑定精确干净提交。验证环境发现源码缺陷时回施工环境修复，不能在验证副本补文件后继续
宣称原提交通过。源码、安装头、实际链接和消费者运行需要分别核对。

架构合理性、功能正确性、性能和完整产品闭包分别判定。测试通过不证明职责正确；未执行、未测量、
未归因与外部阻断使用明确状态，不把缺少证据写成通过。

## 15 工作区 文档与变更纪律

复用现有工作树、增量构建和依赖缓存，只保留本轮必要的独立验证副本。保留精简的命令、版本、日志、
原始样本和索引，不默认保存每轮整套源码、对象库、SDK 和符号副本。结束后清理失效产物，受阻时
准确记录，不绕过限制或谎称完成。

保护用户修改、未合并工作和冻结参考源码。格式、语义和迁移改动保持可审查；只提交授权范围的文件，
不通过 reset、强推或混入用户修改来整理现场。

长期架构和使用说明放文档目录或模块 README，阶段记录与原始验证材料保存在源码树外。规则应说明
适用条件和成因；模块特有的线程数、作用域数量、协议、设备和性能阈值留在模块说明中。

AGENTS.md 负责可反复执行的工程约定，本文解释共同设计原则，模块文档描述具体合同。三者保持一致，
不把过时阶段方案扩散成多份相互矛盾的永久规范。

## 16 评审时应能回答的问题

1. 这个类型和函数实际负责什么？动作是否归正确对象，名称是否准确？
2. 哪份数据是权威，哪些是派生结果，是否存在重复身份或状态？
3. 谁拥有资源，谁借用，什么时候可以转移、复用和释放？
4. 同步完成、异步完成、取消、部分失败和关闭分别如何结束？
5. 是否存在隐藏提交、等待、分配、回调重入或过宽上下文依赖？
6. 零变化、稀疏变化、批量工作和并行使用的复杂度分别是什么？
7. 类型、头文件、target、安装和消费者是否完成同一次迁移？
8. 每项结论由源码、可观察行为或可重复测量中的什么证据支持？

回答不清楚时，应先调整职责、数据和阶段顺序，不通过更多包装、共享保活或重复判断把问题隐藏起来。
