# RD2-D0｜内部歧义裁决与候选正文入库指令

**性质：用户设计裁决 / 文档勘误，不是生产代码实施授权。** 适用 `codex/render-v2` 的 RD2-D0 文档阶段；执行前重新确认远端 HEAD。旧 FINAL、原 ZIP、四张 CSV、F0–F4 历史证据以及 `render_legacy/**` 不得修改。RD2 未获用户批准前仍是 Candidate，不得自称生效中的 FINAL。

## 1. 四项强制裁决

**A｜保持 Core 已有身份域。** 数据的稳定语义类型继续采用 `RenderDataTypeId`（原 `renderDataTypeId(canonical_name)`），独立于 `SceneCapabilityId`、`FeatureTypeId`、Graph Definition 局部的 `GraphResourceId`。不得发明与其平行的全局 `GpuTypeId`、GenericDependencyId 或以某个 GPU Buffer handle 代表数据类型。`DataSet` 的实例身份仅用于 Scope 内具体 `{scope owner, RenderDataTypeId, DataSetKey, generation}` 的解析/验证；它是 runtime-local、须携带有效 scope/generation 的 handle，不成为另一种全局、可跨 Runtime 随意比较的 TypeId。`RecordHandle<T>` 只在对应 DataSet 上有效（携带 DataSet 身份或由 DataSet-bound reader/writer 严格限定），避免同 T 的不同 DataSet 内索引碰撞。`ShaderOwnerId/BindingSlotKey` 是结构性布局身份，不能包含某 Scene/View 的 DataSet 实例 ID，也不能以 descriptor set 数字作为 owner 身份。

**B｜保留既有 C0–C13 编号与职责，不重新命名已经验收的 compiler 阶段。** RD2 的 `C1 Data/Provider Resolve`、`C11 Barrier/state/alias planning`、`C12 Queue schedule/indirect/record recipes` 等表述必须纠正。准确合同：

| 编号 | 既有 FINAL 职责 |
|---|---|
| C0 | Canonicalize（Graph 作者声明、资源范围与 ID） |
| C1 | Resolve（**Graph 内** required/optional producer、semantic provider、import/export 和 fallback） |
| C2 | Validate Interfaces（PassSchema 与 Graph/Shader 资源访问接口契约） |
| C3 | Build Versioned Hazard Index（版本、RAW/WAR/WAW、range） |
| C4 | Topological Schedule（确定性拓扑、冲突与 cycle 检测） |
| C5 | Root/SideEffect Reachability（保留可达有用 Pass） |
| C6 | Lifetime/Usage（逻辑生存期与有效 usage） |
| C7 | Scope & View Group Proof（Scene/View/Target 合法共享证明） |
| C8 | Emit LogicalPlan（不可变中立编译结果） |
| C9 | Layout/Shader（完整 shape、重定位、LayoutPlan） |
| C10 | Physical resources（原生存储/物理资源和内存约束） |
| C11 | Native pass execution（PSO、不可变 Native 录制/绑定配方） |
| C12 | Queue/sync（BarrierProgram、Queue schedule、Ownership/Wait/Signal） |
| C13 | Executable assembly（完整的 `ExecutableGraphPlan` 候选与退休合同） |

以后确需扩展步骤，也应先在功能归属层写明确输入与输出，不通过重排 C 编号冒充已验收原阶段的新职责。

**C｜将 DataSet/Feature Requirements 解析置于 Graph Compiler 之前。** 同一个 Backend/Runtime 的**冷态 Feature Composition** 依次验证 Feature/Capability 注册、`{scope, RenderDataTypeId, key, schema version, read/write authority}`、required/optional/fallback、多 Writer 冲突，输出已绑定的 DataSlot/View 及**中立、结构性 StorageInterfaceShape**。此过程不创建第二 Graph Compiler，也不在热路径使用字符串 Type Registry。Feature 使用已解析的 Typed DataView 贡献 `RenderGraphBuilder` 资源和 Pass（根据 PassSchema 降低为 Buffer/Image 及确切读写/producer）。随后 **C1 只负责 Graph 的 producer/semantic/import/output 解析，C2 只核对 Graph Pass 资源接口**。如果 CPU DataSet 仅作为某个 Feature 的能力依赖，没有真实 GPU Pass 读写，不制造伪 Graph Pass 或 Barrier；如果来自 GPU Compute，则由实际 Pass Producer/版本建立 RAW/WAW/WAR；CPU Dirty Upload 的 GPU Ready Ticket 在 Native Import/同步路径表达。实际 DataSet/NativeBacking 的 Invocation 绑定与结构性 Shader/Plan Cache Key 分开。

**D｜区分 CPU 数据、Wire、GPU ABI 三类约束。** `DataSchema<T>` 描述数据的语义身份、类型字段、作用域/权威、变更模型和通用存储资格；**CPU-only 数据**不要求 `std::is_trivially_copyable_v<T>`、`std::is_standard_layout_v<T>` 或合法 std430。`CpuStorage` 所需的 C++ 生命周期/移动/拷贝能力由其真实 Storage 策略约束。仅在发布跨线程/ABI 消息时应用已有 `PacketValue`/生成的 `WireSchema` 与明确的编码、所有权约束；不能用 `memcpy(C++ struct)` 假冒 wire 格式。仅当数据实际以 Shader-visible Record 表示时，才要求生成的 `GpuLayout<T>`（或者显式 `GpuRepresentation<T>`）与 SPIR-V 反射验证 Offset、Stride、Alignment、类型、版本和必要 Capability；C++ CPU struct 不必与 GPU record 字节布局相同，必要时生成可验证的打包/上传转换。Native Image、外部 Import 具有各自的合法物理描述，不一律化约为 `StorageBuffer<T>`。**同一原有 meta-generator 同源生成可选的 CPU/Wire/GPU 合同**，绝不新加第二解析器。`RenderDataDescriptor` 既有 `wire_version/layout_version/size/alignment` 不得在文档中静默改成 GPU ABI Fingerprint；GPU Layout Identity 作为经审批的后续可选能力单独记录。

可使用如下**概念性** C++20 约束说明（不是要求 D0 实施 C++）：

```cpp
template<class T>
concept DescribedData = requires { DataSchema<T>::descriptor(); };

template<class T>
concept GpuRecord = DescribedData<T> && requires {
    requires GpuLayout<T>::validated;
};
// WirePacket 继续按已有 Transport PacketValue 及生成的 wire contract 检查。
```

**注意**：`GpuRecord` 不是所有 `DataSchema<T>` / `TypedStorage<T>` 的前提；只有 GPU-facing typed Buffer view、GPU direct record encoding 才应用它。

## 2. 避免 Graph ↔ Storage 规划循环

正确顺序：

```
Data type registration + Scope data declarations
  -> Feature Composition resolves Dataset & Capability requirements
  -> Freeze neutral StorageInterfaceShape / structural BindingSlotKey
  -> Feature PassSchema contributes Graph resources and Pass access
  -> Existing Logical Graph C0–C8 unchanged
  -> Existing Native C9–C13, C10 chooses compatible native backing/placement
  -> Invocation maps structural slots to real DataSet backing with GPU ready/last-use tickets
```

`StorageInterfaceShape` 是先于 Graph 的约束，不是已经分配好的 GPU Buffer；C10 只能选择不改变已冻结 Shader-visible ABI 的合法物理 backing。具体 DataSetId、Camera、当前 Buffer handle、普通 dirty revision 不得让相容 Shader Pipeline Layout 每帧重编译。涉及 GPU layout/Shader stage/Buffer capability 的变化才按既有 native key 规则判断是否生成新候选。
