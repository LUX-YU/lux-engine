# Render 设计哲学与工程规范

本规范面向 Render 的设计、实现和审查，整理历次重构中已经明确的取舍。目标是让职责、数据流和
释放顺序可以沿代码直接读懂，在此基础上取得真实渲染性能。它不是阶段计划，也不表示当前源码已经
满足全部条款。

用户最新明确裁决优先；工程通则见 [AGENTS.md](../../AGENTS.md)，格式配置见
[.clang-format](../../.clang-format)，当前 API 使用方式见
[Render README](../../modules/function/render/README.md)。历史计划用于理解成因，不能覆盖后来的裁决。
本文不授权新的功能或扩大施工范围。

## 1 设计的优先顺序

首先保证身份、内存、线程、GPU 使用顺序和业务终态正确。随后优先处理职责和数据算法，再优化真实
热路径；源码行数、类型数量和局部微基准只是辅助指标。

“简洁”应当体现为调用链短、事实来源少、状态转换明确。把一段清楚的流程拆成多个包装类，或者为了
减少几行代码而隐藏所有权转移，都不构成简化。允许删除和重新组织不合理的类、函数与文件，不能因为
它已经提交、已经被测试覆盖，就把现有类边界当成不可改变的前提。

### 1.1 每项机制必须有实际职责

增加长期对象前，必须说明它负责什么、持有什么、被谁使用、何时结束，以及已有对象为什么不能承担
这项责任。优先使用已有对象、局部值和算法函数；没有独立状态的算法不必成为常驻类。

不得通过新的 Manager、Host、Owner、Adapter 或 Registry 补偿错误的职责划分。已经具有明确职责的
唯一 CommandRegistry、Storage 定位目录和执行上下文不因此删除，也不能在旁边再建一份同义权威。
stdexec 的 Sender、Receiver 和 OperationState 是执行协议，不以名称相似就判定为冗余。

### 1.2 复用成熟代码时保留算法依据

Legacy 是分页实例流、Geometry Arena、材质参数表、Bindless 和绘制算法的重要来源。优先阅读并迁移
实际代码，而不是只借用术语后重新实现一个更低效的版本。保留数据布局、GPU ABI、增量复杂度和失败
回滚的依据；不把旧框架、固定材质族或按帧号推测完成的做法一并恢复。

人工编写的 gapi 是接口表达、轻量句柄和集合释放方式的参考。Render 现已采用 NRI，不能为了沿用旧
计划再维护一套平行 Vulkan 资源实现。保留成熟算法不等于冻结旧的模块边界。

冻结 Legacy 只作参考，不改其源码、不链接它来补齐新实现，也不把尚未迁移的算法宣称为已具备。

## 2 动作归执行者 数据保持本义

动作属于真正执行该动作的对象。数据记录可以描述工作、保存位置或借用资源，但不应反向指挥创建它
的系统。

```cpp
queue.recordAndSubmit(record);
arena.release(range);
outbox.flushTo(responder, budget);
```

这些关系表达 Queue 提交、Arena 归还范围、Outbox 发布回复。不要让 CommandBatch 因为保存了一个
Queue 指针而自行提交，让 Range 自行调度 Arena，或让 Attachment 自己遍历并修改整个 Server。

这不禁止必要的反向借用。订阅连接需要定位被订阅对象，Sender 需要执行设施，Arena Range 需要定位
Segment。判断依据是借用是否支持它的真实职责，而不是“结构里出现指针就不纯粹”。

拥有上下文与实现上下文的算法是两回事。设备会话可以组织设备设施的存续，但不因此亲自决定专业
纹理默认值、材质表形状、场景关系或所有帧执行策略。初始化、推进和销毁应各归实际执行者。

接口名称必须暴露关键副作用。查询不应在第一次调用时悄悄创建默认资源并提交 GPU 工作；完成派发
不应以一个模糊名称同时承担上传提交。确需组合的流程，在上层调用点明确写出顺序。

## 3 一份事实由一个位置负责

不同种类的状态需要区分，不能因为它们都叫“状态”就合并，也不能为同一事实维护多套标志。

| 事实 | 责任边界 |
|---|---|
| 哪个材质引用哪个纹理 哪个实例使用哪个 Mesh | Client 的业务权威数据 |
| 某个运行时句柄当前是否有效 | 唯一生成式身份表 |
| Render 如何组织 GPU 数据及其 CPU 镜像 | 对应专业 Storage |
| 哪批 GPU 工作已接纳或完成 | 唯一物理 Queue 的提交与完成事实 |
| 哪个请求已经产生什么结果 | Command 执行结果及原 IPC 路由 |
| 哪个 Frame slice 可以重写 | 实际 CPU 写入状态及相关 Queue 完成条件 |

不重复维护 `alive/reserved/retired/reference/lease` 来解释已有容器成员关系和 generation 已经表达的
事实。确实存在的 `updating`、Staging 容量、帧写入计数和发布尾栈保护应保留，它们不是同一个事实。

稳定名称用于冷态发现；Command、Handler、Feature、Storage 类型和 Storage 实例使用各自身份域。
拿到已验证 ID 后直接索引，不再沿层级重复名称查找。Hash 不能单独证明名称、类型或布局相同。

## 4 Client 和 Render 的责任边界

### 4.1 Client 决定业务关系和操作顺序

Client 决定资源创建、引用、更新、解绑与释放顺序。Render 不自动发现 Material→Texture、
Instance→Mesh/Material 的业务依赖，不通过 Observer 网络替 Client 改写其它 Storage。

例如，修改材质贴图应由 Client 发出明确材质更新请求。解析请求中的无效 Texture 句柄时可使用规定的
白图默认值；这不意味着已经写入 GPU 的材质索引会在另一资源被删除时自动更新。Client 仍须显式处理
未来引用，不能以默认白图规则代替解除引用。

Client 应在删除 Storage 前结束相关上传并解除未来消费者。任意提前删除不是取消协议。不得为宽容
错误调用顺序而保活整个 Storage、维护共享依赖图或增加补偿状态机。

### 4.2 Render 仍负责内部物理事实

Client 不负责 VkBuffer/NRI Buffer 地址、Arena 扩容、Descriptor 更新、GPU 完成和物理释放顺序。
这些是 Render 的职责，不能反向推给 Client。

Render 可以保留必要的 CPU 镜像，以组织稀疏更新、补齐其它 FIF slice 或构造实际 GPU 数据；不保留
没有消费者的上层资产镜像和完整描述副本。内部 Buffer 地址变化通知与业务依赖传播不同：前者只更新
真实受影响的绑定，不能扫描并重算整个场景。

### 4.3 借用输入有明确结束条件

上传源采用只读借用。提交成功后，Client 保持源地址、范围和内容有效，直到收到该请求的 Response。
SUCCESS、FAILED、CANCELLED 均须在最后一次 CPU 读取结束之后产生；入队失败不取得借用。

abandon、断连或回复无法送达，都不能证明读取已结束。没有 Response 时，由应用清偿 Server 和 CPU
生产者后释放输入。Render 不为这项调用合同增加 Source Payload 共享拥有层。

配置由请求或实际使用对象独占，冷态构建同步借用。异步操作需要的数据随唯一请求转移，不复制
`shared_ptr<const Config>`。提供类型操作、删除器或回调的模块必须存活至对象析构和回调退栈；
这项代码寿命由应用装配和关闭顺序保证。

## 5 所有权与轻量资源

### 5.1 RAII 放在真实拥有者

Storage、Context、Queue、Arena 等实际集合负责创建、失败回滚、移交和最终释放。Buffer、Image、
Descriptor、Range 等高基数记录只保存句柄、分配身份及实际需要的数据，不逐个保存重复的 Device、
Allocator、删除器、映射状态和堆 Impl。

拥有者自己的析构已经可以表达 RAII，不要求再用智能指针重复表达每个成员的固定释放方法。选择
值式成员、句柄还是独占指针，要依据可选性、地址稳定性、异构性和实际移动需求。

`unique_ptr` 没有引用计数，也不自行额外分配它指向的对象。应删除的是不必要的独立 `new`、两层
对象和动态删除器。确实被回调或 Range 借用的稳定地址不能在“去智能指针”时失效。

Render 自有资源路径不使用 `shared_ptr`、`weak_ptr`、SharedBytes 或改名的引用计数网络来补偿
关闭顺序。stdexec、NRI 或资产库内部的实现不据此机械改写；若出现真正的新共享寿命需求，先说明
独立消费者与结束条件，不能自行恢复共享资源框架。

### 5.2 轻量句柄不能掩盖拥有权转移

聚合句柄上的 `std::move` 不保证清空源。转移必须按实际记录明确置空，不能覆盖仍有效的资源而遗漏
释放，也不能让两个记录同时声称拥有同一个物理对象。

```cpp
destination = std::exchange(candidate, {});
```

这要求 destination 已为空或其原资源已按合同移交。指针为空、generation 失效和 GPU 已完成分别
代表不同事实，不能互相替代。

底层分配与释放必须配对。NRI 对象使用对应 NRI 销毁入口；VMA 分配不能用裸 Vulkan 销毁冒充完整
释放。VmaAllocation 是每个分配的身份，不等于可以从设备统一取回的 VmaAllocator。

## 6 stdexec 管执行 GPU 完成决定物理清理

### 6.1 上传保留标准执行机制

保持这条职责链：

```text
类型化 Command
  → Handler
  → 专业 Storage 的 Sender
  → UploadContext 准备 Staging 并组织批量 Copy
  → Queue 接纳必要提交并建立后续使用依赖
  → Storage 发布实际资源及句柄
  → RenderThread 发布 Response
```

专业 Sender 持有操作私有输入和未发布产物，通用上传不解释 Material/Mesh 的业务发布规则。CPU
工作使用已有调度器，采用候选、改写目录和发布回复回到 RenderThread。

同步 Handler 直接填写 Response，不为统一外观创建 Sender、Pending 或 Future。异步 Command 的
connected OperationState 由 `counting_scope + spawn` 管理，不恢复自定义 OperationState 表。
结果交付记录只携带已完成结果和路由，不再次拥有操作状态。

真实 GPU 完成源可以有必要的 Sender 和借用回调节点；不能为了让代码出现更多组合器，增加第二条
队列、第二个线程池或每专业类型一套调度桥。

### 6.2 唯一物理清理作用域

所有物理延迟清理只进入 DeviceSession 的 `cleanup_scope_`。Arena、Segment、Storage、Context、
Descriptor 和 Staging 不各自增加清理 Scope，也不恢复 RetirementQueue、Permit、Lease 或另一张
资源拥有表。

`command_scope_` 与 `cleanup_scope_` 分别承担业务操作停止和不可省略的物理清偿，不是重复机制。
`spawn` 管理 connected OperationState 的分配、启动和销毁；Scope 跟踪关联与 join。Scope 本身
不保存资源目录，不判断 GPU 完成，同属 Scope 也不会自动建立操作间顺序。

销毁是 GPU 安全条件满足后的 CPU 动作，不是可录进 GPU CommandBuffer 的“销毁命令”。
业务取消不能提前结束已接纳 GPU 工作的物理清理。

### 6.3 多 Queue 登记与回调顺序

1. 停止未来使用后，在同一个不可挂起的设备调用段捕获相关物理 Queue 已接纳前沿。角色别名先去重，
   后来的无关提交不延长本次条件。
2. 一次启动所有子等待并完成登记，不等完 Queue A 才登记 Queue B，也不在登记中切线程或派发回调。
3. 每条 Queue 按完成值顺序派发，同值保持登记顺序。先摘节点再调用，调用之后不再访问可能已经销毁
   的节点；不能用“已经完成就立即回调”越过先前尚未派发的清理。
4. 全部相关条件结算后，执行清理；普通错误、超时和 stopped 不等于 GPU 已完成。DeviceLost 按真实
   设备终态清偿，不宣称正常成功。
5. Arena Range 先登记归还，Segment 的最终清理后登记，并覆盖此前使用。Range 归还在完成回调内结束，
   不二次排队；最后才销毁 Segment 的元数据和 Buffer。

Arena 没有局部 Scope。上述顺序依赖 Queue 登记、完成和回调规则，而不是依赖全局 Scope 的计数。
清理操作不得捕获已经可能销毁的 Storage/Arena 的 `this`；应承接移出的物理数据及仍有效的设施借用。

### 6.4 关闭必须保持完整的顺序

关闭准入，停止并清偿业务操作；持续推进 CPU、RenderThread 和 GPU 完成；结束输入读取、结算回复；
清偿请求后关闭 Responder；停止未来录制并解除绑定；逻辑对象移交全部物理清理；关闭并 join 唯一
cleanup scope；最后释放清理所借用的设施、Queue 与设备。

Scope join 不证明外部 Producer 的回调栈已经返回。发布尾栈、模块寿命和必要的生产者 join 仍有
独立职责。依赖 RenderThread 继续推进的工作不能用阻塞 `sync_wait` 卡住同一线程。

直接在析构体中销毁设备时，须先清偿仍会调用设备的成员；C++ 成员析构发生在析构函数体之后。
不能删除一个 RAII 包装后，继续依赖已经不成立的旧成员销毁顺序。

## 7 帧阶段与真实 FIF

### 7.1 执行阶段可见

一轮推进明确区分：接纳请求、观察完成、派发就绪工作、确定可复用帧槽、准备 CPU 数据和 Descriptor、
录制、提交、接纳后发布。各阶段之间传递实际数据和已建立的条件，不靠隐藏回调重新进入上层流程。

Begin、Record、End、Submit 位于同一个不可挂起的段中。准备数据、可能失败的创建和容量等待尽量在
取得录制资格前完成；准备回调不得趁调用者已 Begin 时另行提交或派发完成。

### 7.2 FIF 是资源独立与完成约束

Queue 有三个提交槽不等于 FIF=3。需要同时证明：

- GPU 仍可能读取的动态数据有独立物理 slice，或有另一个明确成立的读写顺序。
- 参数、Descriptor、间接数据、页表和 Target 输出按实际用途处理在途重写。
- 帧槽复用同时满足 CPU 写入结束及所有参与物理 Queue 完成。
- CPU 业务镜像和不可变程序仍保持单份；不能给每份物理 slice 再复制一套业务权威。

并非所有资源都必须按 FIF 复制。不可变资源可以由多个帧读取；动态资源是否分片由访问关系决定。
帧状态属于实际执行流程，设备提供硬件能力与完成条件。不能为了收窄一个类而把同一份多 View
帧协调状态复制进多个 Context。

### 7.3 批处理必须覆盖实际成本

稀疏更新只处理 K 项、脏字和实际上传范围。连续脏范围跨字合并，再按真实页、Buffer、布局和有限
Staging 窗口拆分；不能合并 Submit 后仍逐脏字产生大量 Copy。

范围只有在实际提交接纳后才确认。分块、失败和其它 slice 尚未补齐的脏标记必须准确保留，不能扩大
“已上传”范围。已知有序连续输入采用直接路径；不重复为 Client 已去重数据排序去重。必要的脏页
排序只服务范围归并。

共享资产在多个 View 间复用。准备集合在结构变化时维护，不每帧重新发现、排序整个资源图。合并提交
必须保持依赖和错误边界；不能任意重排重叠写入，或通过增加 Queue 容量掩盖饥饿。

### 7.4 CPU 与 GPU 等待集中管理

最小化等待次数，明确等待哪个已接纳条件以及它阻塞什么。禁止每资源、每 Chunk 或每 View 无条件
`waitIdle`，禁止用固定 sleep 降速，也不为降低请求时延改成无界忙等。

有工作时持续推进；空闲使用现有可唤醒等待；GPU 饱和时采用有界等待并兼顾请求和各 View 的进度。
等待上限、窗口大小等是可测量策略，不是不可改变的架构常量。

## 8 专业数据与编译边界

| 领域 | 应负责的数据与算法 | 不应混入的职责 |
|---|---|---|
| Mesh Storage | VBO/IBO Arena、Section、稳定记录与范围复用 | 全场景 Draw 分组和可见性 |
| Instance Storage | 分页字段、CPU 镜像、稳定槽、dirty range、GPU slice | 一套宣称适用所有算法的固定 Instance ABI |
| Material Storage | 消费 Cooked 程序布局、连续参数表、稳定材质槽、局部更新 | 重推 Shader ABI 或自动维护 Client 的贴图关系 |
| Texture Storage | 采样图像、Mip/Region、实际 Descriptor 引用 | 替 Material 自动传播业务更新 |
| Feature | 声明供需、参数、Pass 和绘制方式 | 稳定帧重复动态构图 |
| Compiler | 解析一次接口与布局，降低为执行计划 | 查 Server 业务状态或重新生成第二份 Graph |
| ExecutionContext | 实际动态绑定和帧资源 | 维护上层资产或 Camera 业务 |

固定 GPU 记录公开真实数据结构；可变 Material 参数公开并消费 Cooked 布局。不能以“GPU 数据公开”
为由定义一个巨大固定材质结构，也不能让 Storage 根据参数数量重新计算 Shader 已确定的 offset、
stride 和 block 布局。

编译决定逻辑 set/binding 和资源需求；Attach 创建或解析物理 Storage，落实到 Context 的实际资源
记录。两者时序不矛盾，不需要为此保留兼任订阅拥有者、参数信封和上传任务的长期 Binding 大包。

必要地址变化只更新实际受影响绑定。Storage 负责自身数据更新；Feature 描述 Draw，Compiler 降低
描述，执行代码调用 Draw/Dispatch。Camera 和视锥作为专业参数输入，不成为通用 View 的固定 ABI。

只保留唯一逻辑 Graph/Analysis。不能为兼容旧职责再建一份图、IR 或相同资源的第二份计划。History、
完整 GPU Culling、WSI/HDR 等未来能力须单独实施与验证，不能由现有字段、Queue 槽或示例名字推定。

## 9 Command 错误与边界校验

### 9.1 公开结果使用显式错误字段

```cpp
struct CreateMeshResponse final
{
    RenderError error{};
    MeshId mesh{};
};
```

Response 的 `error.type == 0` 表示成功；失败时业务字段按合同处理，不消费半构造结果。不能普遍宣称所有
Response 都是平凡类型：拥有字符串、vector 的结果仍是实际 C++ 对象，也不能因此直接 memcpy。

当前直接 IPC 模型不自动返还已消费的原 Request。入队失败保留原输入；已接纳后的失败恢复依赖
Response 业务信息和 Client 权威状态，不能把过时的 TypedRenderCompletion 恢复接口写回规范。

类型资格在安装/绑定冷态比较完整名称、ABI、尺寸、对齐及适用的存储表示；动态目录通过生成式 ID
分发。不同 Client 相同数值 RequestId 仍沿各自来源回复，不能按数值合并路由。

### 9.2 内部返回值依真实语义选择

| 语义 | 选择 |
|---|---|
| 只有真假含义 | `bool` |
| 没有失败生产者 | `void` 或自然值 |
| 值与多个实际错误原因 | `expected<T, Error>` |
| 后端状态本身已完整 | 保留后端结果，在模块边界映射一次 |
| 已有稳定数据 | `const T&`、`span` 或明确的可空借用 |
| 大结果且不能确认廉价移动或消除复制 | 调用方提供输出引用，明确失败后输出状态 |

不能把 DeviceLost、容量不足和不支持格式压成一个 bool；也不能给必然成功的内部设置套三层
expected。考虑真实构造/移动成本，不把返回类型体积大直接等同于复制昂贵。

### 9.3 检查放在有效边界

保留外部请求、身份/代际、类型、范围、实际失效和 GPU 状态变化检查。前序验证与所有权不变量已经
保证的条件，不在下游每层、每个 Draw 重新校验。异步期间真实状态可能变化的采用点仍需按合同验证。

先完整验证一批请求，再修改业务状态。未发布候选失败保持旧状态；已发生的原位修改或 GPU 副作用
不能伪装为已经回滚。`OUTCOME_UNKNOWN` 用于确实无法确定的结果，不把所有发生过 Copy 的候选失败
一律归为 Unknown。

普通堆 OOM 为 fatal。可恢复设备分配、显式容量和后端错误保留准确原因；不虚构普通 new 的可恢复
错误，也不为缩短判断而丢掉真实 GPU 错误。

生产代码不主动抛异常，不使用 RTTI。异常只允许在工程明确的外部隔离边界转换；不添加热路径
try/catch，不全仓启用禁异常编译开关。实机必须成立的失败处理不能只用会被 NDEBUG 删除的 assert。

Render 只输出结构化错误和 RenderErrorSink 诊断，不直接决定终端、文件或日志落点。

## 10 命名和模块可见性

### 10.1 名称描述实际合同

名称应回答“是什么”和“做什么”。避免单独用 `api/state/data/context/work` 代替领域含义，不用
Host/Owner 作为 Lux 自有类型、文件或字段的泛称，也不把它们机械换成 Provider/Manager。
第三方 API 和标准术语保持原名，文本说明应写明具体执行线程与对象。

| 实际内容 | 名称原则 |
|---|---|
| NRI Core 函数表 | 明确 NRI 与接口身份，如 `nri_core_`，不只叫 `api_` |
| Vulkan 互操作扩展 | 明确 backend，如 `vulkan_extensions_`；同时控制可见范围 |
| 类型 metadata | `Descriptor`，不是一个伪装成实例的 Storage |
| 实际 Command 方法集合 | `CommandHandler`，不叫纯数据式的 `Commands` |
| 回传完成结果的工作项 | 表达 Delivery，不误称执行状态的拥有者 |
| 位置选择值 | `Location`，不叫 Owner |
| 类型化操作参数或范围记录 | 保持数据意义，不暗含上层控制器 |

Storage 名称限定数据和算法用途。例如索引三角网格与 meshlet 不是同一个 MeshStorage 配两个实例键。
稳定类型名确定合同；实例 key 选择同一类型的实例；人可读 description 解释用途和限制，不参与 ABI
相等或热路径派发。

### 10.2 一个 Render 库 四类顶级目录

| 目录 | 可见性 |
|---|---|
| `include/` | 安装的 Command、ID、配置、必要 GPU 数据合同、Descriptor 和真实应用 API |
| `sinclude/` | 项目级扩展与装配接缝，不安装；需要 GPU 的扩展显式依赖选定后端 |
| `pinclude/` | 具体内置 Feature/Storage/Handler、私有算法与实现细节 |
| `src/` | 与实际职责对应的实现 |

Render 保持一个正式库 target，不为概念目录制造多个无独立消费者的库。公开描述不泄露具体实现；
也不能借“只公开 Descriptor”删除 Client 必需的请求、ID 和 GPU 数据格式。

NRI/Vulkan 类型不进入安装公共头。仅隐藏公共头不足以自动取得多后端资格；后端专属查询、等待和
内存维护应局限在相应实现中，不通过一个公开 `vk()` 入口扩散到专业代码。

头文件只包含声明所需依赖。实现重依赖放源文件或私有头；数据头不拉入行为模块。迁移类型、命名空间、
目录和 target 时同步迁完消费者与安装清单，不留下兼容别名、空 target 或废弃安装头。

gapi 保持纯头文件。可选 VMA 宏不改变同名类型 ABI，不在头中定义 VMA_IMPLEMENTATION；分配路径
必须能区分。此规则不要求 NRI Render 恢复已经淘汰的 gapi/VMA 后端实现。

## 11 C++ 与 CMake 风格

遵循项目格式配置和所在模块约定；不以格式化工具输出覆盖已经明确的人类可读性要求。

- C++20；四空格缩进，花括号按项目 Allman 风格，控制流不省略必要 braces。
- 类/struct 使用大写驼峰；成员函数小写驼峰；成员小写下划线，private 成员加末尾下划线。
- `enum class` 类型名使用 `E` 前缀，枚举项全大写下划线；variant 别名使用 `V` 前缀。
- `public/protected/private` 与类的花括号同级。相邻函数定义之间留一个空行。
- 单条语句不超过 120 列且层次清楚时保持一行；超过后按语义和参数换行，不拆成难读的碎片。
- 长返回类型先用有意义的别名；多行初始化、调用和声明的闭括号独占下一行并正确对齐。
- 多个独立校验用具名 `const bool` 分组，最后判断组合结果；不得破坏指针、范围、溢出检查的短路安全。
- 注释说明不变量、借用范围、提交点、线程和非常规算法原因，不用注释替错误命名辩护。
- lambda 适合局部捕获与组合；不能用巨大捕获对象隐藏新长期拥有者，或用深层 lambda 掩盖职责划分。
- CMake 参数按语义分组，结束括号独占一行，相邻调用留空行。一个生产源只由真实所属 target 编译。

格式整理、语义修改与测试迁移应可分别审查；不格式化冻结 Legacy 或用户未提交代码。

## 12 性能依据和工程节奏

### 12.1 性能评估以实际工作量为准

优先评估多 View 稳定帧、资源流送、全量/稀疏 Transform、材质更新和真实 Draw。同时检查调用深度、
分配次数与字节、内存峰值、复制量、Copy/Barrier/Submit 数、同步点及算法复杂度。

已知 ID 直接索引；更新收集和退休在零变化时不随 live 数量全扫；K 项更新随 K 和脏范围增长。冷态名称排序、图分析和
小物理 Queue 集合扫描有合理用途，不为表面 O(1) 引入额外表和重复状态。

稳定帧不做 Feature 动态构建、Graph Analysis、名称查找、Shader/Pipeline 编译或普通堆分配。
异步请求可以有合理分配，不能为了空 Sender 微基准退回自制 OperationState 拥有机制。

CPU 镜像、FIF 补写和 Staging 可能各有必要复制。应逐段列明数据来源、目的及字节量，再删除无用
复制；不能用“零拷贝”口号隐藏借用延长或数据缺失。

正式比较固定工作量、配置和测量边界，按已约定的至少 10 对独立进程交替取样，保存逐 run 的
p50/p95/p99/max 和异常样本。Validation、故障注入、包装计数和 VTune 采样与正式时延分开。
5% 是既有同工作量退化的工程参考线，未归因继续 PARTIAL，不把所有噪声或新工作量判为同一种退化。

VTune 的 CPU Time、等待、GPU 时间及 Client 输入准备不能混算。未知驱动地址不伪装成已定位函数；
没有硬件计数器就不宣称 cache miss 或锁竞争原因。默认策略只在有因果证据和公平性验证后调整。

### 12.2 完成一个大模块后集中验证

日常允许必要编译诊断与静态检查，不按每个函数、类型或小提交反复运行全套矩阵。一个职责闭环迁完
接口、实现、消费者和失效路径后，集中构建、运行和审查；正确性门禁失败不推进依赖阶段。

正式验收运行授权范围的 `all -j 4 -- -k 0`。配置或 CMake 变化后再构建一次确认 no work。
构建与实机验证串行。涉及 GPU/异步寿命的修改保留真实 GPU、Validation/SyncValidation 和 ASan
证据；不删除失败目标、削弱断言或恢复旧接口来取得绿色。

最终独立验证绑定精确 clean commit，先做 tracked snapshot 检查。发现生产缺陷回施工环境修复，
不能在验证副本补头或改源码。安装、链接、头可见性及实际消费者是闭包的一部分，不能由一个示例
运行成功代替。

每项结果分别报告架构、功能/GPU 安全、性能和产品闭包。未运行是 NOT_RUN，未测量是 NOT_MEASURED，
未解释是 PARTIAL，外部阻断是 BLOCKED；测试通过不证明类型职责正确。

### 12.3 工作树 磁盘与文档

复用主工作树和增量构建目录，独立验收只保留本轮必要的一份副本。共享依赖和工具链；旧新性能比较
保留必要可执行程序，不复制整套仓库、SDK、对象文件和 PDB。结束后清理失效产物，遇到删除限制如实
记录，不绕过限制，也不谎称已清理。

用户修改、未合并提交、Legacy 冻结文件与历史资格受保护。提交只包含授权变更，推送到当前授权分支；
不能把历史分支名永久当作任何后续任务的推送目标。

公开头变化按仓库约定同步三个安装前缀，依据精确提交并避免混入用户修改。Android 头同步不代表
Android 构建通过；默认不扩展到未授权的平台或上层产品验证。

架构和使用规则放 `docs/` 或模块 README。施工计划、性能样本、失败日志和验收证据放源码树外，
历史源码从 Git 查询；不恢复 `.internal` 状态账本，不为制造 V SHA 添加空提交。

## 13 已撤回做法与尚待裁决的实现

以下取舍已经明确，后续不能从旧文档重新引入：

| 旧做法 | 现行方向 |
|---|---|
| 每个 Buffer/Image 都必须独立 RAII 并带释放环境 | 轻量物理记录，真实集合负责寿命 |
| Source/Config/物理资源普遍共享保活 | Source 借用，Config 独占，物理值进入清理操作 |
| Arena 自己再设清理 Scope | 唯一 DeviceSession cleanup scope，按 Queue 顺序清偿 |
| Runtime 手工拥有异步 connected OperationState | stdexec spawn/scope |
| 上传 Response 必须等待最终 GPU 完成 | 必要提交接纳、使用顺序成立、Storage 发布后返回；完成决定复用/清理 |
| 生产 Readback 和公共 Ticket 维持整个框架 | 不恢复该上层功能；必要 Copy、映射及内部完成事实保留 |
| 已接纳失败回复自动返还原 Request | 当前类型化 Response 模型，入队失败仍保留输入 |
| Resource/Feature/Native 各维护可相互补偿的状态层 | 一份权威数据，明确借用与提交点 |
| 各阶段复制整套源码和构建长期保存 | 一份活动施工现场，一份必要独立验证，精简证据 |

最新讨论确认需要继续收窄 DeviceSession 职责，但具体 Frame 状态承载位置、共享采样表的实际拥有者、
后端私有接缝及哪些低基数对象改为值式成员，仍需在下一份实施方案中统一确定。本文不把某个临时
字段名、DescriptorSet 归属或尚未验证的类拆分写成已完成的架构。

## 14 设计评审的最低回答

每个有实质影响的修改应能回答：

1. 哪个对象负责这件事，为什么是它？名称是否准确表达数据与动作？
2. 唯一拥有者、借用者、借用结束点、CPU 发布点和 GPU 安全点分别是什么？
3. 是否新增重复身份表、状态、配置副本、资源依赖或生命周期机制？
4. 工作是否在正确阶段执行？有没有隐藏提交、等待、分配或回调重入？
5. K 项变化、零变化、多个 View 与多个在途帧的成本分别是什么？
6. 采用和失败是否准确？已接纳 GPU 工作、取消和回复失败是否被混淆？
7. 真实消费者、删除项、安装闭包是否一起迁完？还有没有兼容层替旧设计续命？
8. 结论由源码、实际数据和可复现验证中的哪一项支持？哪些仍未证明？

无法回答时先修正职责与流程，不通过新增包装、共享保活或重复判断让问题暂时不可见。
